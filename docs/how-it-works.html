How it works

A short mental model of the library — enough to adapt it on your team, without a file-by-file tour.

JSON shape

Every entry is a { "type", "value" } envelope. type picks the node class (double, PIDController, folder, …). value is a primitive, an array, or a nested map of child entries. 

{
  "Arm": {
    "type": "folder",
    "value": {
      "PIDController": {
        "type": "PIDController",
        "value": {
          "p": { "type": "double", "value": 0.1 },
          "i": { "type": "double", "value": 0.01 },
          "d": { "type": "double", "value": 0.001 }
        }
      }
    }
  }
}

Paths like Arm/PIDController/p walk that tree. Folders group; composites (PID, Pose2d, …) hold named fields; scalars/arrays are leaves editable over NetworkTables.

Runtime flow

  1. ConfigManager loads robot-config.json into a typed document and publishes under /Config.
  2. In debug, NT edits update the live tree and autosave config-cache.json. Getters read that live document.
  3. In match, NT is display-only. Getters read the JSON defaults from startup. No JSON writes.
  4. Promote with /Config/Save or when the watched layout file content changes — that writes robot-config.json.
  5. Subsystems use ConfigDocument typed getters (getDouble, getPIDController, getPose2d, …).

Live PID vs rebuilt pose

  • Live composites (PID, ProfiledPID) keep one WPILib object and update it in place so a subsystem can hold a reference across loops.
  • Immutable composites (Pose2d, feedforwards, units, …) rebuild a fresh value when a child scalar changes — call the getter when you need the current object.

Errors: warn vs fail

  • Warn and continue — missing path, wrong getter type, missing composite field. Logs to System.err with a [Config] prefix and returns a safe default so a typo does not crash the robot.
  • Fail loudly — missing/invalid JSON file, unknown type string. Startup should not pretend a broken file is fine.

Look for [Config] in the Driver Station console when values look wrong. See troubleshooting.
